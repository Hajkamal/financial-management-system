# اصلاح امنیت — مرحله اول، پیش‌نویس آزمایشی

مبنای تغییرات: کامیت `51cef90d04778f73c8aa84e1baeab0191753cfcf`.

**این نسخه برای ادغام در main یا استفاده واقعی آماده نیست.** شاخه آزمایشی نباید به دیتابیس اصلی وصل شود. SQL در هیچ سرور واقعی اجرا نشده است.

## اصلاحات انجام‌شده

- Supabase Auth تنها مسیر ورود است. ورود محلی، ساخت کاربر جعلی در App، مدیرشدن با ایمیل ثابت، اعتماد به user_metadata و تغییر هویت مرورگری کنار گذاشته شدند.
- پروفایل/مجوز از RPC دیتابیس با اتصال صریح `auth_user_id = auth.uid()` می‌آید. کاربر فاقد پروفایل فعال دسترسی ندارد. نقش‌ها و اتصال‌ها باید توسط مدیر معتبر بازبینی شوند.
- SQL فقط نقش مدیر با مجوز canManageUsers را برای تغییر پروفایل‌ها مجاز می‌کند؛ کاربر نمی‌تواند خودش نقش/مجوز یا UUID احراز هویت تخصیص دهد. حتی مدیر مرورگری نمی‌تواند ستون password را SELECT کند.
- کارکرد قدیمی JSON و توکن مشترک از سرور توسعه حذف و کلاینت قدیمی بدون درخواست شبکه غیرفعال شده است.
- رمزها در DTO کاربر و SELECT مرورگر وجود ندارند؛ مالی/کاربران در کش جدید مرورگر ذخیره نمی‌شوند. **کش قدیمی حذف نشده**؛ حذف دستی فقط بعد از بکاپ تأییدشده انجام شود.
- پاک‌سازی خودکار ۱۴۰۴ حذف شده و فیلتر حذف سال در بارگذاری برداشته شده است.
- ذخیره تکی تراکنش RPC با قفل ردیف و row_version است. تغییر با نسخه قدیمی، ساخت تکراری یا حذف با نسخه قدیمی رد می‌شود. ساخت رکورد، هویت ثبت‌کننده را از پروفایل معتبر می‌گیرد.
- salary_year و salary_month بدون پاک‌کردن رکوردها اضافه و در تبدیل داده حفظ می‌شوند. مقادیر تاریخی به‌صورت حدسی پر نمی‌شوند.
- API هوش مصنوعی توکن را با getUser سرور بررسی می‌کند، مجوز/سهمیه را از دیتابیس می‌گیرد، نرخ را بین نمونه‌های Serverless مشترک نگه می‌دارد و خطاهای محرمانه سرویس را برنمی‌گرداند.

## محافظ‌های انتشار

`VITE_ENABLE_FINANCIAL_WRITES` به‌صورت پیش‌فرض فعال نیست؛ UI و سرویس‌های این مرحله فقط خواندنی هستند. **این گزینه کنترل مجوز امنیتی نیست**؛ RLS/RPC کنترل امنیتی واقعی هستند. تا اتمام مرحله دوم این گزینه را روی true نگذارید، حتی برای استفاده اصلی.

`ENABLE_EXTERNAL_AI` هم پیش‌فرض خاموش است. تنها پس از تأیید ارسال داده به Gemini، برای سرور آزمایشی تنظیم شود. VITE_ در ابتدای کلید خصوصی هرگز استفاده نشود.

## مراحل راه‌اندازی صرفاً در پروژه آزمایشی

1. بکاپ قابل بازیابی از پروژه زنده تهیه و نسخه فعلی سورس را حفظ کنید. متغیرهای Preview را به یک Supabase آزمایشی جدا متصل کنید.
2. ساختار و داده‌های موردنیاز آزمایش را به پروژه آزمایشی منتقل کنید. فایل `supabase-security-hardening.sql` را بازبینی و فقط روی همان پروژه اجرا کنید.
3. نقش، وضعیت و permissions موجود در app_users را بازبینی کنید. اجرای SQL به داده‌های قدیمی مشروعیت خودکار نمی‌دهد.
4. حساب آزمایشی را از مسیر مدیریتی Supabase Auth بسازید؛ کاربران قدیمی app_users خودبه‌خود به حساب Auth تبدیل نمی‌شوند. تأیید ایمیل باید مطابق سیاست پروژه انجام شود.
5. یک مدیر SQL معتبر، UUID حساب تأییدشده را به پروفایل درست متصل کند. فقط اتصال صریح لازم است؛ مثال زیر آموزشی و غیرقابل‌اجرای مستقیم است:

```sql
-- فقط روی پروژه آزمایشی، بعد از تطبیق هویت حساب و پروفایل:
UPDATE public.app_users
SET auth_user_id = '<confirmed-auth-user-uuid>'::uuid
WHERE id = '<reviewed-app-profile-id>';
```

6. کلید عمومی و URL مرورگر باید هر دو متعلق به همان پروژه آزمایشی باشند. برای AI سمت سرور نیز `SUPABASE_URL` و `SUPABASE_ANON_KEY` باید همان پروژه را نشان دهند. کلید service_role لازم نیست و نباید به مرورگر داده شود.
7. ورود، خروج، عدم دسترسی کاربر بدون اتصال، وضعیت pending/inactive و نقش‌های مختلف را در Preview بررسی کنید. داشتن فایل‌ها یا بازشدن صفحه، جای این آزمون را نمی‌گیرد.
8. این پیش‌نویس را با main ادغام نکنید و فایل SQL را روی دیتابیس اصلی اجرا نکنید.

## تست‌های اجراشده

۳۹ تست محلی روی Node 24: تست SQL با PostgreSQL جاسازی‌شده PGlite و داده ساختگی، تست جریان API با SDK/provider شبیه‌سازی‌شده، و بررسی نحوی فایل‌های TypeScript/TSX. هیچ درخواست Gemini پولی یا اتصال به Supabase واقعی در تست‌ها انجام نشده است.

تکرار تست در یک نسخه محلی و خارج از دیتابیس واقعی:

```bash
npm install
npm install --no-save --package-lock=false @electric-sql/pglite@0.5.8
node --test tests/security.test.mjs
```

این نصب صرفاً ابزار تست را به محیط محلی اضافه می‌کند. فایل‌های lock محلی حاصل از تست را بدون بازبینی commit نکنید.

**Build کامل مخزن، tsc کامل، تست مرورگر، Vercel واقعی، SQL روی Supabase آزمایشی و بازیابی بکاپ هنوز تأیید نشده‌اند.** تست syntax همان build نیست. تست API mock همان تست زنده Supabase نیست.

## کارهای باقی‌مانده قبل از انتشار

- عملیات حقوق، اقساط، فاکتورها و بستن سال باید چندرکوردی/اتمیک شوند؛ برخی handlerهای قدیمی هنوز خوش‌بینانه هستند. write guard عمداً مانع فعال‌شدن آن‌ها است.
- کاربران: ایجاد/دعوت، اتصال امن حساب‌های قدیمی و تغییر رمز مدیریتی باید با API مدیریتی مناسب تکمیل شوند. فعلاً این عملیات و ثبت‌نام عمومی غیرفعال‌اند.
- بکاپ/بازیابی، پاک‌سازی دسته‌جمعی و ارسال کل داده دستگاه غیرفعال‌اند؛ باید به مسیر تراکنشی، مجوزدار و دارای تأیید صریح منتقل شوند.
- customCategories، لوگو و لاگ تغییرات باید ذخیره پایدار و کنترل دسترسی مناسب بگیرند؛ API فایل قدیمی دیگر مسیر جایگزین نیست.
- حفاظت از آخرین مدیر، حذف وابستگی‌ها (از جمله CASCADE کارمند/حقوق)، اعتبارسنجی تاریخ جلالی و سیاست خواندن اطلاعات حساس باید تکمیل/تست شوند.
- بررسی وابستگی‌ها و رفع آسیب‌پذیری‌های کتابخانه‌ها، از جمله نسخه فعلی xlsx، باقی است.
- خروج موفق SDK به معنی لغو فوری همه JWTهای صادرشده نیست؛ تست خروج و سیاست عمر/لغو نشست‌ها لازم است.
- مجوزها، لینک Auth، نسخه کد و اجرای SQL باید در انتشار نهایی هماهنگ باشند؛ برگشت فقط کد بدون بررسی سازگاری دیتابیس امن نیست.
