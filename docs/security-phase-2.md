# مرحله دوم: Supabase + Vercel — آماده آزمون، نه انتشار مستقیم

این سند جایگزین محدودیت‌های موقت مرحله اول برای این شاخه است. این کد به پایگاه داده فایل JSON متکی نیست و داده واقعی یا کلید خصوصی همراه کد ارسال نمی‌شود.

## اصلاحات
- هویت JWT توسط Supabase Auth بررسی می‌شود. نقش، وضعیت و مجوز از پروفایل فعال متصل به Auth UUID خوانده می‌شود؛ metadata قابل ویرایش کاربر مجوز ایجاد نمی‌کند.
- ده جدول موجود حفظ می‌شوند؛ خواندن و نوشتن مالی از API سروری و RPCهای محدود انجام می‌شود. مرورگر حق دسترسی مستقیم به جدول‌های مالی و رمزهای قدیمی ندارد.
- داده مالی جدید فقط در حافظه مرورگر است؛ کش مالی قدیمی خودکار حذف یا وارد نمی‌شود.
- ثبت اسناد مرتبط، حقوق، قسط و مالیات با تراکنش اتمی و نسخه سراسری انجام می‌شود. تغییر هم‌زمان به خطای conflict منتهی می‌شود، نه بازنویسی بی‌خبر داده.
- پیش از هر ثبت مالی/پروفایل، نسخه پیشین با AES-256-GCM رمزگذاری و در همان تراکنش ذخیره می‌شود. شکست بکاپ باعث لغو ثبت است.
- مدیر مجاز با ورود در ده دقیقه اخیر می‌تواند بکاپ فعلی یا ۵۰ نسخه خودکار اخیر را دانلود کند. بازیابی نیازمند انتخاب فایل و تأیید صریح است؛ حساب‌های کاربری و ممیزی مالی با بازیابی مالی جایگزین نمی‌شوند.
- فایل دانلودی بکاپ رمزگذاری‌شده نیست؛ آن را محرمانه و خارج از دیتابیس نیز نگهداری کنید.
- ایجاد حساب از Admin API انجام می‌شود. حساب بدون پروفایل فعال مجاز نیست. حذف کاربر منطقی است و آخرین مدیر فعال محافظت می‌شود.
- خروج و تغییر رمز، از جمله recovery، نشست‌های قبلی سامانه را مسدود می‌کنند. AMR ورود بررسی می‌شود تا refresh توکن نشست قدیمی را احیا نکند.
- لوگو و دسته‌بندی‌ها در Supabase ذخیره می‌شوند. فرم‌های اصلی منتظر تأیید ذخیره می‌مانند.
- حذف ممیزی، حذف گروهی سال ۱۴۰۴ و جایگزینی کل داده با کش دستگاه غیرفعال است.

## متغیرهای سرور

- `SUPABASE_URL`: آدرس پروژه.
- `SUPABASE_ANON_KEY`: کلید عمومی برای Auth و RPC محدود.
- `SUPABASE_SECRET_KEY`: کلید خصوصی secret یا legacy service_role؛ **فقط سرور**.
- `BACKUP_ENCRYPTION_KEY`: کلید تصادفی ۳۲ بایتی، base64؛ فقط سرور و یک نسخه مستقل در محل امن.
- `APP_URL`: آدرس اصلی سایت.
- `APP_ORIGINS`: آدرس‌های دیگر مجاز، جداشده با کاما، در صورت نیاز.
- `FINANCIAL_WRITES_ENABLED`: تا پایان تأیید پیکربندی `false`؛ پس از تأیید `true`.
- `ENABLE_EXTERNAL_AI`: ارسال به Gemini پیش‌فرض خاموش؛ فعال‌سازی نیازمند تصمیم آگاهانه درباره ارسال prompt است.

`VITE_SUPABASE_URL` و `VITE_SUPABASE_ANON_KEY` برای Auth مرورگر باقی می‌مانند. کلید خصوصی و کلید بکاپ هرگز پیشوند VITE ندارند. کلید بکاپ را بدون برنامه مهاجرت تغییر ندهید؛ کلید اشتباه/گمشده باعث غیرقابل خواندن‌شدن آرشیو قبلی می‌شود. Vercel با `npm ci` و package-lock نصب می‌کند.

## انتشار هماهنگ

1. قبل از هر SQL، بکاپ مستقل داده و ساختار، Auth و Storage در صورت استفاده تهیه کنید. CSV ساختار جدول‌ها بکاپ داده نیست. آرشیو داخل همان دیتابیس در برابر حذف کل پروژه کافی نیست.
2. `supabase-security-hardening.sql` خودکار هنگام deploy اجرا نمی‌شود. ابتدا روی پروژه مجزا/کپی داده بررسی شود. SQL علاوه بر جدول‌های برنامه، trigger تغییر رمز روی `auth.users` اضافه می‌کند.
3. پروفایل‌های موجود فقط پس از بررسی هویت به UUID درست Supabase Auth متصل شوند. نمونه برای حساب بررسی‌شده:

```sql
UPDATE public.app_users
SET auth_user_id = '<VERIFIED_AUTH_UUID>'::uuid
WHERE id = '<VERIFIED_PROFILE_ID>';
```

هیچ اتصال خودکار بر اساس ایمیل و هیچ ساخت خودکار مدیر از مرورگر وجود ندارد. رمز قدیمی به صورت خودکار به Auth منتقل نمی‌شود؛ ایجاد/دعوت حساب‌های فاقد Auth و تنظیم رمز باید جدا بررسی شود.
4. Preview برای آزمایش نوشتن نباید به دیتابیس اصلی متصل باشد. کلیدهای سرور و کلید رمزنگاری در محیط درست تنظیم شوند.
5. ورود دو نقش، ثبت/ویرایش/حذف مجاز، حقوق و قسط و مالیات، خروج و دانلود/بازیابی بکاپ در پروژه مجزا بررسی شوند. سپس SQL و کد به شکل هماهنگ منتشر شوند. SQL جدید، دسترسی مستقیم نسخه قدیمی را قطع می‌کند؛ rollback صرفاً با Vercel کافی نیست. برای برگشت، سیاست دسترسی عمومی قبلی را دوباره باز نکنید.
6. بعد از تأیید حساب مدیر و صحت داده، نوشتن فعال و PR از Draft خارج و با main ادغام شود.

## نتیجه و دامنه تست محلی

- ۶۵ تست موفق: PostgreSQL با PGlite و ساختار ارائه‌شده؛ HTTP با Express واقعی، SDK Supabase واقعی و Auth/PostgREST ساختگی.
- `npm run lint`: موفق.
- `npm run build`: موفق.
- `npm audit`: صفر آسیب‌پذیری شناخته‌شده در نتیجه این اجرا؛ این به معنای تضمین امنیت کل برنامه نیست.

تست‌ها با داده ساختگی انجام شده‌اند؛ صحت ایمیل، تنظیمات پروژه واقعی، عملکرد زنده Vercel و تمام گردش‌های UI در مرورگر تولید را اثبات نمی‌کنند. اجرای SQL و انتقال حساب واقعی هنوز انجام نشده‌اند.

بکاپ خودکار snapshot برنامه است، نه Auth، Storage، schema یا کل پروژه. تغییر رمز Auth و ثبت پروفایل یک تراکنش مشترک بین دو سرویس نیست؛ خطاهای جزئی گزارش می‌شوند و ایجاد Auth بدون پروفایل با حذف حساب تازه جبران می‌شود.

آرشیو فعلاً پاک‌سازی خودکار ندارد و با هر ثبت رشد می‌کند. ظرفیت Free plan، نسخه بیرونی و سیاست نگهداری باید جدا مدیریت شوند. snapshot کامل برای حجم کم/متوسط طراحی شده؛ با رشد داده، API صفحه‌بندی/تغییرات جزئی لازم است. حد ورودی API و بازیابی ۳ مگابایت است؛ فایل بزرگ‌تر به مسیر مدیریتی جدا نیاز دارد.

ستون password قدیمی برای حفظ داده موجود پاک نمی‌شود، اما در API و بکاپ مالی نمایش داده نمی‌شود. حذف آن پس از انتقال کامل حساب‌ها و بکاپ امن، تصمیم جداگانه است.

## بررسی تکمیلی روی کپی بکاپ واقعی
کپی محلیِ ۲۴۱ رکورد ده جدول، با SQL جدید و تبدیل‌کننده‌های واقعی سرور آزمایش شد. اعتبارسنجی، رفت‌وبرگشت رمزنگاری بکاپ و ثبت اتمی با حفظ مقادیر مالیِ سطح برنامه موفق بود. upsert شرطی فقط ردیف‌های واقعاً تغییرکرده را ویرایش می‌کند؛ تاریخ و نسخه اسناد تغییرنکرده حفظ می‌شود. این آزمون روی کپی محلی است، نه اجرای مالی روی دیتابیس اصلی یا تأیید ورود و ایمیل واقعی در محیط آنلاین.
